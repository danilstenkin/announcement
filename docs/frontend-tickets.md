# Ручки тикетов (review-tickets) — подробный справочник для фронта

Тикет (`ReviewTicket`) — это карточка автоматически сформированного анонса, которая
проходит ревью: сотрудник её смотрит, редактирует, подтверждает дату, согласовывает
и публикует. Этот документ описывает все ручки раздела: назначение, вход, выход,
смысл каждого поля, побочные эффекты и ошибки.

---

## 0. Общие сведения

### Базовый префикс
```
/auto-announce/tickets
```
Через BFF-шлюз перед этим путём добавляется его базовый префикс — уточнить у бэка.

### Заголовки авторизации
| Заголовок | Обяз. | Описание |
|---|---|---|
| `X-User-Id` | нет | UUID текущего пользователя. Пишется в историю как автор действия (`actor_id`). **Если передаёшь — обязан быть валидным UUID**, иначе действие упадёт с 500. Не уверен — не передавай (тогда автор = null). |
| `X-User-Name` | нет | Имя пользователя. На бэке применяется `unquote`, поэтому кириллицу/пробелы слать **URL-encoded** (`%20` и т.д.). Пишется в историю как `actor_name`. |

В отличие от раздела `/announcements`, тут заголовки **опциональны** — `401` не кидается.
Они влияют только на запись «кто сделал» в истории.

### Формат времени
Все даты в ответах — строки ISO 8601 в **UTC** (`2026-05-31T22:04:00+00:00`).
На фронте показывать в Алматы (UTC+5):
```js
new Date(value).toLocaleString("ru-RU", { timeZone: "Asia/Almaty" });
```

### Формат ошибок
Стандартный FastAPI:
```json
{ "detail": "Текст ошибки" }
```
HTTP-код: `400` (нарушены условия действия), `404` (тикет не найден),
`422` (невалидное тело/параметры).

## 1. Справочники значений

### 1.1. `status` — сырой статус тикета (поле `status`)
Машинный статус. Жизненный цикл:
| Значение | Смысл |
|---|---|
| `PENDING_REVIEW` | тикет создан системой, ещё никто не взял в работу |
| `IN_REVIEW` | в работе у сотрудника |
| `REVISION` | возвращён на доработку |
| `AGREED` | согласован, анонс создан и стоит в очереди на публикацию |
| `PUBLISHED` | опубликован |
| `REJECTED` | отклонён |
| `APPROVED` | легаси-статус старых закрытых тикетов (до фичи планирования) |

### 1.2. `display_status` — статус для UI (поле `display_status`)
Производное значение для цвета/ярлыка в интерфейсе. Вычисляется на бэке из `status`,
`publish_confirmed` и состояния публикаций. Использовать его для отображения, а
`status` — для логики.
| Значение | Когда возникает | Цвет (ТЗ) |
|---|---|---|
| `NO_DATE` | дата публикации не подтверждена | бордовый |
| `IN_PROGRESS` | дата подтверждена, тикет в работе/на доработке | жёлтый |
| `AGREED` | согласован, есть запланированная (`SCHEDULED`) публикация | — |
| `OVERDUE` | дата была, но публикацию отменили (вернулись в работу) | красный |
| `ON_APPROVAL` | на согласовании у руководителя (задел, пока не используется) | фиолетовый |
| `PUBLISHED` | опубликован | — |

### 1.3. `action` — тип записи истории (поле `history[].action`)
`CREATED` (создан системой), `ASSIGNED` (назначен), `TAKEN` (взят в работу),
`SENT_TO_REVISION` (на доработку), `EDITED` (отредактирован), `APPROVED`
(согласован), `REJECTED` (отклонён), `SCHEDULED` (запланирован), `RESCHEDULED`
(перенесён), `PUBLICATION_CANCELED` (публикация отменена), `PUBLISHED` (опубликован).

### 1.4. `source` — источник письма (поле `source`)
`ServiceDesk`, `komek`, `other`. Определяется по адресу отправителя.

## 2. Объекты ответа (описание каждого поля)

### 2.1. `TicketListOut` — элемент списка тикетов
| Поле | Тип | Null? | Описание |
|---|---|---|---|
| `id` | UUID | нет | Идентификатор тикета. Используется во всех ручках действий. |
| `email_id` | UUID | нет | Идентификатор исходного входящего письма, из которого создан тикет. |
| `status` | string | нет | Сырой статус (см. 1.1). Для бизнес-логики. |
| `assignee_id` | UUID | да | Кто взял тикет в работу (id). Null — не назначен. |
| `assignee_name` | string | да | Имя исполнителя. |
| `sender_email` | string | да | Email отправителя исходного письма. |
| `source` | string | да | Источник: `ServiceDesk/komek/other` (см. 1.4). |
| `title` | string | да | Заголовок анонса (его правят в `edit`). |
| `ai_summary` | string | да | Краткое содержание письма от ИИ (одно предложение). Для оператора напрямую не показывается. |
| `created_at` | string | да | Когда тикет создан (ISO, UTC). |
| `updated_at` | string | да | Когда последний раз изменён (ISO, UTC). |
| `display_status` | string | да | Статус для UI/цвета (см. 1.2). |
| `recommended_publish_at` | string | да | Дата публикации, рекомендованная ИИ (ISO, UTC; обычно полночь Алматы). |
| `publish_at` | string | да | Подтверждённая дата публикации (ISO, UTC). Заполняется в `confirm-date`/`publish`. |
| `publish_confirmed` | bool | нет | `true` — дата подтверждена и тикет можно согласовывать. |
| `announcement_id` | UUID | да | Идентификатор анонса. Появляется после `approve`/`publish`. До этого null. |
| `history` | HistoryOut[] | нет | Полная история действий по тикету (см. 2.3). |

### 2.2. `TicketDetailOut` — карточка тикета
Содержит все поля `TicketListOut` **плюс**:
| Поле | Тип | Null? | Описание |
|---|---|---|---|
| `body` | string | да | HTML-тело анонса (то, что увидят операторы). Правится в `edit`. |
| `script_ru` | string | да | Скрипт оператора на русском. |
| `script_kz` | string | да | Скрипт оператора на казахском. |
| `original_html_key` | string | да | Ключ оригинального HTML исходного письма в MinIO (для просмотра «как пришло»). |
| `attachments` | AttachmentOut[] | нет | Вложения исходного письма (см. 2.4). В списке тикетов их нет — только здесь. |

### 2.3. `HistoryOut` — запись истории
| Поле | Тип | Null? | Описание |
|---|---|---|---|
| `action` | string | нет | Тип действия (см. 1.3). |
| `actor_id` | UUID | да | Кто сделал действие. Null — система. |
| `actor_name` | string | да | Имя автора действия (или «system»). |
| `comment` | string | да | Комментарий: причина доработки/отклонения, текст подтверждения даты и т.п. |
| `changes` | object | да | Только для `EDITED`: какие поля изменились, формат `{ "поле": {"old": ..., "new": ...} }`. Для `body` значения заменены на «...» (не раздувать). |
| `created_at` | string | да | Когда произошло действие (ISO, UTC). |

### 2.4. `AttachmentOut` — вложение письма
| Поле | Тип | Null? | Описание |
|---|---|---|---|
| `id` | UUID | нет | Идентификатор вложения. |
| `filename` | string | нет | Имя файла. |
| `object_key` | string | нет | Ключ объекта в MinIO. **Это не URL.** Готовой ручки скачивания вложений тикета пока нет — скачать по нему напрямую нельзя. |
| `content_type` | string | да | MIME-тип (`image/png`, `application/pdf`, …). |

## 3. Ручки

### 3.1. Список тикетов

**Назначение:** получить список тикетов для очереди работы (главный экран раздела).
По умолчанию скрывает закрытые (`APPROVED`/`REJECTED`).

```
GET /auto-announce/tickets
```

**Query-параметры:**
| Параметр | Тип | Обяз. | Описание |
|---|---|---|---|
| `status` | string | нет | Фильтр по сырому статусу (см. 1.1). Если указан — отдаются только тикеты с этим статусом (включая `APPROVED`/`REJECTED`). |
| `assignee_id` | UUID | нет | Фильтр по исполнителю. |

Если `status` не передан — возвращаются все тикеты, **кроме** `APPROVED` и `REJECTED`.
Сортировка — по `created_at` убыванию (новые сверху).

**Тело запроса:** нет.

**Ответ `200`:** массив `TicketListOut` (см. 2.1).

**Ошибки:** `422` — невалидное значение `status`/`assignee_id`.

---

### 3.2. Карточка тикета

**Назначение:** получить полные данные одного тикета для экрана обработки (тело,
скрипты, вложения, история).

```
GET /auto-announce/tickets/{ticket_id}
```

**Path-параметры:**
| Параметр | Тип | Описание |
|---|---|---|
| `ticket_id` | UUID | Идентификатор тикета. |

**Тело запроса:** нет.

**Ответ `200`:** `TicketDetailOut` (см. 2.2).

**Ошибки:** `404` «Ticket not found».

---

### 3.3. Назначить исполнителя

**Назначение:** назначить тикет на конкретного сотрудника (распределение работы
руководителем/диспетчером). Переводит в работу.

```
POST /auto-announce/tickets/{ticket_id}/assign
```

**Тело запроса (`AssignRequest`):**
| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `assignee_id` | UUID | да | Кому назначить (id пользователя). |
| `assignee_name` | string | да | Имя исполнителя (сохраняется в тикет и историю). |

**Побочные эффекты:** `assignee_id/assignee_name` проставляются, `status → IN_REVIEW`,
в историю пишется `ASSIGNED`, уходит событие операторам.

**Ответ `200`:** `{ "status": "assigned" }`

**Ошибки:** `400` «Ticket is already closed» — если статус `APPROVED`/`REJECTED`.

---

### 3.4. Взять в работу

**Назначение:** сотрудник берёт тикет себе (self-assign). Исполнитель — текущий
пользователь из заголовков.

```
POST /auto-announce/tickets/{ticket_id}/take
```

**Тело запроса:** нет. Исполнитель берётся из `X-User-Id` / `X-User-Name`.

**Побочные эффекты:** `assignee` = текущий пользователь, `status → IN_REVIEW`,
в историю `TAKEN`, событие операторам.

**Ответ `200`:** `{ "status": "taken" }`

**Ошибки:** `400` «Ticket is already closed».

---

### 3.5. Вернуть на доработку

**Назначение:** отправить тикет обратно исполнителю на доработку с комментарием
(например, руководитель не согласен с формулировкой).

```
POST /auto-announce/tickets/{ticket_id}/revision
```

**Тело запроса (`RevisionRequest`):**
| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `assignee_id` | UUID | да | Кому вернуть на доработку. |
| `assignee_name` | string | да | Имя исполнителя. |
| `comment` | string | да | Причина возврата (попадёт в историю и уведомление). |

**Побочные эффекты:** `assignee` обновляется, `status → REVISION`, в историю
`SENT_TO_REVISION` с комментарием, событие операторам.

**Ответ `200`:** `{ "status": "revision" }`

**Ошибки:** `400` «Ticket is already closed».

---

### 3.6. Редактировать контент

**Назначение:** правка текста анонса перед согласованием (заголовок, тело, скрипты).
Меняются только переданные поля; ведётся аудит изменений.

```
POST /auto-announce/tickets/{ticket_id}/edit
```

**Тело запроса (`EditRequest`)** — все поля опциональны, шлются только изменяемые:
| Поле | Тип | Описание |
|---|---|---|
| `title` | string? | Новый заголовок анонса. |
| `body` | string? | Новое HTML-тело анонса. |
| `script_ru` | string? | Новый скрипт оператора (рус.). |
| `script_kz` | string? | Новый скрипт оператора (каз.). |

Поле учитывается, только если передано и отличается от текущего значения.

**Побочные эффекты:** обновляются поля, в историю пишется `EDITED` с diff
(`changes`), если что-то реально изменилось; уходит событие.

**Ответ `200`:** `{ "status": "edited", "changed_fields": ["title", "body", ...] }`
— список реально изменённых полей (может быть пустым).

**Ошибки:** `400` «Ticket is already closed».

---

### 3.7. Подтвердить дату публикации

**Назначение:** зафиксировать, когда анонс должен опубликоваться. Обязательный шаг
перед согласованием.

```
POST /auto-announce/tickets/{ticket_id}/confirm-date
```

**Тело запроса (`ConfirmDateRequest`):**
| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `publish_at` | ISO datetime | нет | Желаемая дата/время публикации. **Слать с поясом `+05:00`** (Алматы), например `2026-06-01T03:04:00+05:00`. Если не передать — берётся `recommended_publish_at` тикета (полночь Алматы). |

**Побочные эффекты:** `publish_at` = выбранная дата, `publish_confirmed = true`,
в историю — запись о подтверждении даты. **Статус не меняется.**

**Ответ `200`:** `{ "status": "confirmed", "publish_at": "<ISO, UTC>" }`

**Ошибки:**
- `400` «Ticket is already closed» — статус `APPROVED`/`REJECTED`/`PUBLISHED`.
- `400` «No publish date provided and no recommendation available» — не передан
  `publish_at` и нет рекомендованной даты.

> ⚠️ Если прислать `publish_at` без пояса или в UTC, время «уедет» на фронте.
> Всегда добавлять `+05:00`.

---

### 3.8. Согласовать (поставить в очередь публикации)

**Назначение:** одобрить анонс. Создаёт скрытый анонс и ставит его в очередь на
автоматическую публикацию в `publish_at`.

```
POST /auto-announce/tickets/{ticket_id}/approve
```

**Тело запроса:** нет. Дата берётся из `publish_at` тикета (заданного в `confirm-date`).

**Предусловия:** `title` не пустой; `publish_confirmed = true` и `publish_at` задан;
статус не `APPROVED/REJECTED/PUBLISHED` и не `AGREED`.

**Побочные эффекты:** создаётся анонс (`is_hidden = true`), создаётся публикация
`kind=PRIMARY, status=SCHEDULED, publish_at=<дата>`, `status тикета → AGREED`,
проставляется `announcement_id`, в историю `APPROVED`, событие операторам. Анонс
**скрыт** до момента публикации воркером.

**Ответ `200`:** `{ "status": "agreed", "announcement_id": "<UUID>", "publish_at": "<ISO, UTC>" }`

**Ошибки `400`:**
- «Ticket is already closed» — `APPROVED/REJECTED/PUBLISHED`.
- «Ticket already has a scheduled publication» — уже `AGREED`.
- «Cannot approve: title is empty» — пустой заголовок.
- «Publish date must be confirmed first» — не вызывали `confirm-date`.

---

### 3.9. Опубликовать сейчас

**Назначение:** опубликовать немедленно, не дожидаясь запланированного времени.

```
POST /auto-announce/tickets/{ticket_id}/publish
```

**Тело запроса:** нет.

**Логика:** если тикет уже согласован (`announcement_id` есть и публикация
`SCHEDULED`) — публикует существующую запись (без дублей). Иначе создаёт анонс и
публикацию с `publish_at = now` и сразу публикует.

**Побочные эффекты:** анонс становится видимым (`is_hidden=false`, `published_at`
проставлен), публикация `→ PUBLISHED`, тикет `→ PUBLISHED`, письмо `→ DONE`,
уведомление операторам.

**Ответ `200`:** `{ "status": "published", "announcement_id": "<UUID>" }`

**Ошибки `400`:** «Already published» (статус `PUBLISHED`), «Ticket is rejected»
(статус `REJECTED`), «Cannot publish: title is empty».

---

### 3.10. Отменить запланированную публикацию

**Назначение:** снять анонс с расписания (передумали публиковать в назначенное время).

```
POST /auto-announce/tickets/{ticket_id}/cancel-publication
```

**Тело запроса:** нет.

**Побочные эффекты:** активная `SCHEDULED`-публикация → `CANCELED` (с `canceled_at`),
`status тикета → IN_REVIEW`, в историю `PUBLICATION_CANCELED`. Анонс остаётся скрытым.

**Ответ `200`:** `{ "status": "publication_canceled" }`

**Ошибки:** `400` «No scheduled publication to cancel» — нет `announcement_id` или
нет активной запланированной публикации.

---

### 3.11. Отклонить тикет

**Назначение:** отказаться от анонса (не публиковать вообще). Закрывает тикет.

```
POST /auto-announce/tickets/{ticket_id}/reject
```

**Тело запроса (`RejectRequest`):**
| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `comment` | string? | нет | Причина отклонения (в историю). |

**Побочные эффекты:** `status → REJECTED`, исходное письмо `→ DONE`, в историю
`REJECTED` с комментарием, событие операторам.

**Ответ `200`:** `{ "status": "rejected" }`

**Ошибки:** `400` «Ticket is already closed».

---

## 4. Типовой сценарий обработки

```
1. GET /tickets              — открыть очередь
2. POST /{id}/take           — взять в работу        (status → IN_REVIEW)
3. GET /{id}                 — открыть карточку
4. POST /{id}/edit           — поправить текст        (опционально)
5. POST /{id}/confirm-date   — зафиксировать дату      (+05:00!)
6. POST /{id}/approve        — согласовать             (status → AGREED, в очередь)
   └─ воркер опубликует в publish_at  →  status → PUBLISHED
```
Альтернативы на шаге 6: `POST /{id}/publish` — опубликовать сразу;
`POST /{id}/revision` — вернуть на доработку; `POST /{id}/reject` — отклонить.
После согласования передумали — `POST /{id}/cancel-publication`.

## 5. Важные нюансы для фронта
- Время в ответах — **UTC**; показывать в `Asia/Almaty` (+05).
- `confirm-date` — `publish_at` строго **с поясом `+05:00`**.
- Вложения приходят только в карточке (`GET /{id}`), не в списке.
- У вложений тикета пока **нет ссылки на скачивание** (только `object_key`).
- `take/approve/publish/cancel-publication` тела запроса не требуют.
- `X-User-Id`, если передаётся, должен быть валидным UUID.
